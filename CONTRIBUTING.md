# Участие в разработке

Спасибо за помощь проекту. Ошибки и идеи можно обсуждать в Issues будущего GitHub-репозитория. Для крупного изменения сначала опишите проблему и ожидаемое поведение. Не прикладывайте реальные данные студентов или токен бота.

## Окружение

Используйте Node.js 24+, npm и Python 3.10+. Установите зависимости через `npm ci` и `python -m pip install -r requirements-dev.txt` внутри виртуального окружения. Точный порядок запуска описан в [README](README.md).

`package-lock.json` и точные версии инструментов нужны для воспроизводимых проверок. `private: true` запрещает случайную публикацию в npm; это не ограничивает открытую публикацию на GitHub и права MIT.

## Стиль кода

- JavaScript использует ES modules, `const` по умолчанию, `let` при изменении значения, строгие сравнения. Prettier задаёт формат; ESLint проверяет ошибки и неиспользуемые значения.
- Python форматируется Ruff: четыре пробела, понятные имена, импорт стандартной библиотеки отдельно от внешних пакетов.
- Для новых функций выбирайте имена по назначению. Комментарии объясняют ограничения и причины решений, а не повторяют строку кода.
- Пользовательские строки — на русском. Имена модулей и API — на английском. Документируйте публичные контракты и неочевидные правила.
- Общую бизнес-логику помещайте в `public/model.js`, `actions.js`, `profile.js`, `features.js`. Там нельзя обращаться к DOM, Telegram API или диску. Код `public/` доступен любому посетителю: секретов в нём быть не должно.
- HTML с пользовательскими данными формируйте через `escapeHtml` из `public/ui.js`. Комментарий `/* HTML */` включает форматирование шаблона, но **не экранирует данные**.
- Авторизация и права проверяются на сервере. Скрытая кнопка не является проверкой доступа.
- Несколько связанных изменений базы выполняйте в `Store.transaction`. Не делайте сетевых запросов внутри SQLite-транзакции.
- Не форматируйте сгенерированные расписания и не добавляйте их в Git. Тестовые данные должны быть вымышленными.

## Перед pull request

```sh
npm run format
.venv/bin/python -m ruff format .
npm run check
.venv/bin/python -m ruff check .
.venv/bin/python -m ruff format --check .
.venv/bin/python -m unittest discover -s tests -p 'test_*.py'
```

Тест для исправления ошибки должен воспроизводить её, а не дублировать реализацию. Изменения импорта проверяйте на маленьких синтетических таблицах с объединёнными ячейками и подгруппами. Внешний сайт и Telegram не должны требоваться для обычного запуска тестов.

В pull request укажите проблему, итоговое поведение, выполненные проверки и ограничения. Если меняется интерфейс, добавьте снимок с учебными данными. Если меняется база, опишите миграцию и способ восстановления из резервной копии. Не повышайте версию только ради форматирования.

Вклады принимаются на условиях [MIT](LICENSE). Не добавляйте чужой код или материалы, которые нельзя распространять на совместимых условиях.
